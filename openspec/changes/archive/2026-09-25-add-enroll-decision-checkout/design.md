## Context

See `proposal.md` - Why/What Changes for motivation. Today `app/api/courses/[courseId]/enroll/route.ts` always inserts into `enrollments`, with no price check — see `openspec/specs/enrollment/spec.md`'s existing "Free enrollment in a published course" requirement, which this change extends rather than replaces. `courses.price` already exists (`lib/database.types.ts`), and `components/EnrollButton.tsx` already receives `courseSlug` as a prop, so wiring a slug-based endpoint requires no new prop plumbing.

This story splits the same way `add-catalog-search-price-filter` did:
- The branching decision (free → enroll, paid → checkout) is pure and depends only on a number → unit tests, no network.
- Whether the Route Handler actually writes (or doesn't write) to `enrollments`, and doesn't duplicate on retry, can only be confirmed against a real Postgres/Supabase instance with RLS active → integration tests, following the same real-client pattern established in `lib/queries/getPublishedCourses.integration.test.ts` (admin client to seed fixtures, real endpoint under test via `fetch`-equivalent or direct handler invocation, cleanup in `afterAll`).

## Goals / Non-Goals

**Goals:**
- A pure `decideEnrollAction(price: number): "enroll" | "checkout"` function, unit-tested with no mocks.
- A new `POST /api/courses/[slug]/enroll` Route Handler that resolves the course by slug, applies the decision, and either inserts an `enrollments` row (free path) or returns a simulated `checkoutUrl` (paid path) without writing anything.
- Idempotent free-path behavior: calling the endpoint again for an already-enrolled free course does not create a duplicate row (mirrors the existing courseId-based handler's already-enrolled short-circuit and unique-violation fallback).
- `EnrollButton` calls the new slug endpoint and distinguishes a `checkoutUrl` response from an `enrollment` response.

**Non-Goals:**
- No real payment provider (Stripe, MercadoPago, etc.) integration. `checkoutUrl` is a simulated/stubbed value — shape and exact simulation strategy are an implementation decision below, not a payment integration.
- No changes to RLS policies. The existing `courses` "published or own" and `enrollments` insert-with-check policies (`0002_rls.sql`) already constrain what the handler can write; this change doesn't alter them.

> Revised during implementation: the plan to keep the existing `POST /api/courses/[courseId]/enroll` handler untouched and add a separate `[slug]` sibling route turned out to be impossible — Next.js rejects two differently-named dynamic segments at the same path depth. The existing handler was replaced in place instead of left alongside a new one; see Decisions below.

## Decisions

- **Pure function boundary**: `lib/enrollDecision.ts` exports `type EnrollAction = "enroll" | "checkout"` and `decideEnrollAction(price: number): EnrollAction`, taking only a plain number — no `Course` object, no Supabase types — so it has zero import surface beyond itself and is trivially unit-testable. `price === 0` → `"enroll"`; `price > 0` → `"checkout"`. (Negative prices are already prevented by the `courses.price >= 0` check constraint, so the function does not need to special-case them.)
- **Route location — revised during implementation**: the plan to add a sibling `app/api/courses/[slug]/enroll/route.ts` next to the existing `[courseId]` route turned out to be impossible — Next.js's App Router rejects two dynamic segments at the same path depth with different parameter names (`'slug' !== 'courseId'`), a build-time error, not a runtime one. Resolved (with the user, mid-implementation) by replacing the existing `app/api/courses/[courseId]/enroll/route.ts` in place with the new price-aware logic, keeping the folder name `[courseId]` (forced by the constraint above) while treating its value as a slug throughout — the externally observable path shape and behavior match the acceptance criteria (`POST /api/courses/{value}/enroll`, `{value}` resolved against `courses.slug`); only the internal Next.js segment name differs from the literal `[slug]` originally planned. See the note in `specs/enrollment/spec.md`'s "Enroll endpoint resolves course by slug" requirement.
- **Bearer token auth — added during implementation**: the existing handler only read the session from the `@supabase/ssr` cookie (browser-only). To let the integration test call the real endpoint over real HTTP without fabricating `@supabase/ssr`'s undocumented internal cookie format, the route now also accepts `Authorization: Bearer <token>` and, when present, builds an anon-key client with that token forwarded as the request's `Authorization` header (so RLS still evaluates `auth.uid()` normally — this is not an authorization bypass, just an alternate transport for the same anon-key, RLS-governed client). Cookie-based auth remains the path real browsers use; the Bearer path exists for non-browser callers (tests, and potentially future API/mobile clients).
- **Simulated checkout shape**: the paid-path response is `{ checkout: { checkoutUrl: string, courseId, price } }` (mirroring the existing handler's `{ enrollment: {...} }` success shape). `checkoutUrl` is generated as a deterministic stub path, e.g. `/checkout/simulated/<courseId>`, requiring no external service and no new env var — this is what "checkout simulado" in the acceptance criteria calls for, not a real payment redirect.
- **Duplicate-prevention on the free path**: reuse the existing handler's two-layer approach — check for an existing enrollment first (fast path, avoids a needless insert attempt), and fall back to treating a `23505` unique-violation as a non-error success (race-safe). This is copied logic, not a shared helper, to keep this change's diff scoped to the new route; a future refactor could extract a shared `enrollUser(supabase, userId, courseId)` helper if the two handlers keep diverging.
- **Auth check**: same as the existing handler — `supabase.auth.getUser()`, 401 if absent — applied before the price decision, since an unauthenticated visitor should never learn a course's checkout details or trigger any write.
- **Where the course is fetched**: the handler fetches the course's `id`, `price`, and `status` by slug in one query before branching; RLS's "published or own courses are readable" policy means a non-owner requesting a draft course's slug gets no row back, which the handler treats as 404 — consistent with the existing "Draft course detail hidden" behavior in `course-catalog`.
- **Integration test pattern**: follow `lib/queries/getPublishedCourses.integration.test.ts` exactly — real Supabase project (via `.env.local` credentials, admin client to seed a free and a paid published course + a test user), call the new Route Handler's logic directly (import and invoke, or call the running dev server — implementation detail for tasks.md to resolve) as an authenticated user, assert on `enrollments` row presence/absence and response shape, clean up in `afterAll`.

## Risks / Trade-offs

- ~~[Two enroll endpoints (`[courseId]` and `[slug]`) can drift in behavior over time]~~ — moot: Next.js's routing constraint forced a single endpoint (see Decisions), so there is only one handler to keep consistent.
- [A "simulated" checkout that's too convincing could be mistaken for a real payment integration by someone reading the code later] → Mitigation: name the field/response clearly (`checkoutUrl` under a `checkout` key, with the deterministic `/checkout/simulated/...` path) and comment in the route handler that this is a stub pending real payment integration.
- [Testing the Route Handler's DB behavior against a real project mutates real data if seeding/cleanup has a bug] → Mitigation: same safeguard already proven in `getPublishedCourses.integration.test.ts` — unique slugs/emails per run, explicit `afterAll` cleanup, and a credential-presence check that skips the suite entirely rather than failing noisily when Supabase isn't configured.
